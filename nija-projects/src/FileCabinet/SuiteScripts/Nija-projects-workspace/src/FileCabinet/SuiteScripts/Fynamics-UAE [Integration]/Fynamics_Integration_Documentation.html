1. Introduction & Objectives

This document serves as the technical specification for establishing an automated integration between NetSuite ERP and the Fynamics-UAE e-invoicing platform. Fynamics is a certified tax service provider in the United Arab Emirates (UAE) that facilitates invoice clearance and reporting in accordance with the Federal Tax Authority (FTA) regulations.

The primary scope of the integration includes establishing a secure authentication handshake, maintaining session tokens, and routing transactional details from NetSuite into the Fynamics API endpoints for compliant e-invoice submission and signature.

2. Integration Prerequisites & Dependencies

To successfully implement and execute this integration, the following dependencies and configurations must be provisioned and resolved beforehand:

Prerequisite Item Requirement Details Actions Required / Verification
Fynamics API Credentials Partner credentials containing username and password. Ensure credentials are acquired for sandbox testing. Production credentials will be issued upon testing sign-off.
API Environments URLs for Sandbox (Testing) and Production (Live) environments. Establish whitelisting rules in corporate firewalls if outbound NetSuite calls are restricted.
Invoice Fields Mapping Data-level mappings between NetSuite invoice fields and Fynamics XML/JSON fields. Map NetSuite internal IDs (e.g., standard fields, custom transaction body fields) to corresponding Fynamics schema keys.

Note: Access to Sandbox environments must remain separate from Production configurations. A toggle switch or script parameter in NetSuite should determine the environment context dynamically.

3. Authentication Protocol

The Fynamics-UAE platform secures its endpoints using OAuth 2.0 Client Credentials flow. NetSuite initiates the API session by submitting a POST request with basic authentication headers, receiving a temporary Bearer token in return.

3.1 API Endpoints

The authentication endpoints correspond to the respective environments:

  • Sandbox Endpoint: https://sandbox-uae.fynamicstax.com/api/partner/auth/authenticate
  • Production Endpoint: https://uae.fynamicstax.com/api/partner/auth/authenticate

3.2 Authentication Request Specification

The request must be structured as an HTTP POST containing the following parameters:

Request Element Value Specification Description
HTTP Method POST Required for authentication requests.
Content-Type Header application/x-www-form-urlencoded Declares form-encoded post-body payloads.
Authorization Header Basic username:password Concatenation of Basic keyword and Fynamics credentials.
Developer Note: Standard protocols require credentials to be Base64-encoded. Use N/encode in SuiteScript to encode "username:password".
Body Parameters grant_type=client_credentials
scope=read write		 Required fields within the request payload body.

4. Token Lifecycle Management

The issued access token is transient and remains valid for exactly 1 hour (3,600 seconds). To prevent API throttling, a validation and storage logic must be established in NetSuite.

4.1 Storage Strategy

The token and metadata must be stored in NetSuite using one of the following approaches:

  • Custom Field: A designated custom field on a global configuration page.
  • Custom Record: A specific Custom Record Type (e.g., customrecord_fynamics_token_store) holding a single persistent record. This is recommended.

The token store must capture: (1) Access Token, (2) Acquisition Timestamp, and (3) Expires In.

4.2 Token Verification & Retrieval Logic

When a NetSuite script initiates an outgoing invoice submission, it must execute the validation routine outlined below:

Step 1: Check Token Existence
Query the NetSuite Custom Record/Field to retrieve the stored access token and its acquisition timestamp.
▼
Scenario A: Stored Token is Empty
If no token is stored in NetSuite, skip validation and immediately execute the Authentication Routine (Section 4.3).
Scenario B: Token is Present
Extract the stored Access Token, Acquisition Timestamp, and Expiry Period. Proceed to Step 2.
▼
Step 2: Evaluate Token Expiry
Calculate the difference between the Current Time and the Acquisition Timestamp. Compare it against 3,600 seconds (minus a safety buffer of 60 seconds).
▼
Condition B.1: Token Not Expired
If elapsed time < 3,540 seconds, reuse token. Construct header: "Authorization: Bearer [token]".
Condition B.2: Token Expired
If elapsed time >= 3,540 seconds, trigger authentication. Update token store with new token.

4.3 Authentication & Storage Routine (Pseudo-code)

The following script routine encapsulates the verification and retrieval operations within NetSuite: 

function getValidFynamicsToken() {
    var storedRecord = lookupStoredTokenRecord(); // Retrieve Custom Record
    var now = new Date();

    if (storedRecord) {
        var token = storedRecord.token;
        var acquisitionTime = new Date(storedRecord.timestamp);
        var expiresInSeconds = storedRecord.expiresIn || 3600;

        // Calculate age in seconds
        var ageInSeconds = (now.getTime() - acquisitionTime.getTime()) / 1000;

        // Use a 60-second buffer to prevent mid-flight token expiration
        if (ageInSeconds < (expiresInSeconds - 60)) {
            return token; // Token is valid; reuse it
        }
    }

    // Token is missing or expired; authenticate to obtain a new one
    var response = authenticateWithFynamics();
    if (response.success == 1) {
        // Save the new token data in NetSuite Custom Record
        updateStoredTokenRecord(
            response.data.access_token, 
            now.toISOString(), 
            response.data.expires_in
        );
        return response.data.access_token;
    } else {
        throw new Error("Fynamics authentication failed: " + response.errorMessage);
    }
}
